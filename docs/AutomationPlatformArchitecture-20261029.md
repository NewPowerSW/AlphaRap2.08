# AlphaRap / NPSDK 整体架构建议

日期：2026-10-29。核查宿主基线：`0c24b6c`；核心源码：当前 SDK 工作树的 `FlowProgramModel`、`FlowProgramRuntime`、`FlowProgramGroup`。本文是方案评审，不表示建议的类型、VS 扩展或产品台账已经实现；本轮不改应用代码、不运行设备。

## 推荐结论

目标应是：**一份流程工程，一个执行内核，两种使用入口。** 应用工程师用自定义设计器编排工艺；开发人员在 VS 实现设备能力和复杂函数，并查看同一份流程。需要在 VS 编辑流程时，打开同一个流程编辑器。

上一条“主保存直接双向同步 `.Designer.cs`”的建议，适合作为受控兼容功能，不适合作为全平台默认架构。两边各维护一张图再互相改写，会把控件字段、未保存源码、语言、页面复用和删除标记变成长期合并问题。

这不是全面重写：保留 NPSDK Flow_Chart、Flow_BaseForm、现有运行器、真实设备实例、原生 ResultType 方法、继承发现工具、视觉配置、配方和统一保存，重做它们之间的所有权边界。

## 当前问题的结构原因

1. VS 的控件树、FlowPrograms.xml 和生成的 Flow.g.cs 表达了相互重叠的内容。运行中删除靠 RemovedControls，VS 源码控件仍存在。截图的 Loop5.4 差异就是这种双重所有权。
2. FlowControlSource / PrepareRestore 为兼容旧程序，每次恢复还需要判断源码和记忆谁优先。当前修复能解决已遇到的删除与同名页复用，但不适合作为长期的双向编辑协议。
3. 节点已有 ID，页面主要依赖 ParentPath；资源有些使用 GUID，有些使用控件路径或设备显示名。因此“改名”“移动”“删除重建”对不同对象影响不一致。
4. FlowResources.Capture 从 UI 控件树和各页面汇集运行资源。编辑器、程序执行与页面结构仍有联系。
5. 现有节点结果、常量表和本地生产记录，不能直接等同于产品随转盘移动的持久随行卡。该能力在现有文档中仍属设计提案。

## 建议的职责划分

### NPSDK：流程模型与运行内核

- 流程工程负责模块、页面、节点、坐标、连线、入口、绑定、报警和版本。
- 页面、节点、资源及点位使用稳定 ID；显示名、语言和所在容器路径不作为身份。
- 新增对象生成新身份；重命名和移动保留身份；删除后重建同名对象不会继承旧引用。
- 运行器消费保存发布的不可变计划，输出状态、计时、断点和故障事件，不根据按钮颜色判断流程状态。
- 继续复用 FlowProgramRuntime / FlowProgramGroup、资源占用与实际回调结束等待。这里的 FlowDocument、FlowCanvas 等名称用于说明建议职责，不是本轮新增类。

### AlphaRap：实际资源与应用服务

- 由统一资源目录登记原页面创建的同一批轴、IO、Device、相机/VPP、点位和数据对象；工具箱不重复创建、连接硬件。
- 编辑器读取资源说明和方法契约，运行器按 ResourceId 解析真实实例。VS 预览只读工程元数据，不建立设备连接。
- 继承 AbstractDevice、轴和 IO 等现有父类后，公开业务方法继续自动进入工具箱；无需另建登记工程。应排除普通控件管理方法等非业务接口。
- Setting、Recipe、生产字段和权限仍使用现有服务。ProductManagerForm 是配方入口，MainForm Save 是配置保存入口。
- MiddleLayer 逐渐收敛为启动和服务组合入口；不再往其中增加第二份图恢复、硬件目录或产品台账逻辑。

### 自定义设计器：唯一的流程编排入口

- 继承 Flow_BaseForm 的页面仍保留，内部逐步改为共用画布宿主；画布继续展示熟悉的 NPSDK Flow_Chart。
- 流程工程管理页面和节点，不再同时在该 Form 的 Designer.cs 中保存同一批节点字段、位置和连线。
- 常规动作只让工程师理解：做什么、用哪个实际对象、参数来自哪里、结果写到哪里、下一步去哪。
- 默认显示正常 NEXT；需要分支时再添加 CASE。固定值、配置参数、本次流程结果、当前产品字段明确区分。
- 复杂功能仍由当前 Form 的 ResultType 方法或继承设备类的业务方法提供，不重新引入已删除的 C# 脚本和独立代码模块编辑器。
- C# 决定执行结果，工程文档决定页面、布局和出口目标。删除一个节点不自动删除可被复用的业务函数。

## VS 如何保持一致

推荐分两步：

1. **先共用显示。** VS 的 Form 中放置流程画布宿主，读取同一份流程文档，显示相同的页、节点和连线。节点作为该画布的内部呈现，不再次序列化为另一套原生子控件。这里只承诺设计时预览目标，不等于已经具备 VS 原生的逐节点编辑能力。
2. **再共用编辑。** 从 VS 的“编辑流程”入口打开同一编辑器，或者后续做流程文件专用编辑器。两端调用相同的新增、删除、连接、撤销和校验命令，写同一份文档。

VS 继续设计主页、设置页和普通 WinForms 布局，也继续编写、编译和调试业务函数。仅流程图的所有权转入流程工程。

如果必须用 VS 原生窗体设计器任意拖动每个 Flow_Chart，则需要单独建设设计时序列化与受控导入/导出；不应把普通 partial 方法或运行时读 XML 当作这项能力。当前项目是 .NET Framework 4.8，不能直接套现代 .NET 的 OOP Designer 实现。

开发工程和现场部署读取同一工程格式，读不同的发布副本。Main Save 提交配置不要求现场有源码或 VS。两端同时编辑同一修订时必须检测冲突；VS 未保存缓冲区不能仅靠磁盘哈希发现。主保存保持草稿校验、原子替换、发布快照及失败回滚，不随意加入自动编译或运行中修改计划。

## 运行状态与生产数据

整机由统一会话协调初始化、自动多入口、暂停、恢复、故障和停止；画布只显示它的状态。初始化故障后仍用【初始化】重试当前节点；显式【停止】结束会话，下一次初始化从入口重新开始。保留真实回调退出和资源归还屏障，不用先显示待机来假装停止已完成。

不重新引入用户已拒绝的全机轴/IO 就绪扫描。运行前校验工程结构、类型和绑定，硬件反馈与执行状态由相关动作处理。资源并行应逐步精确声明实际占用，不直接删除现有互斥锁。

点胶转盘需要独立产品随行服务：

- ProductId 关联条码，治具/穴位关联当前产品；每次装入、取出和确认转移有明确记录。
- 点胶、称重、AOI 的实际结果写入该产品的工序事实，而不是只留在节点临时输出或全局 Setting。
- 多工位完成后，通过真实转位到位与定位确认更新工位映射；不能只因发出运动指令就搬移产品数据。
- 装盘先提交本地持久结果和 MES 待传任务，再按接口约定上传、重试及记录业务回执。CSV 作为本地日志/查询出口；网络重试不能使点胶或装盘动作重复执行。
- 异步结果携带产品及本次操作身份，避免结果写到转位后的另一件产品。掉电恢复需要核对真实位置和在制品；不把“重跑软件初始化”当作产品状态恢复。

现有 DataForm 继续用于字段配置和记录查询，现有本地写入能力可复用；可靠产品台账、位置恢复和 MES 待传队列仍需实现，不能宣称本轮已经具备。

## 渐进实施顺序

### 第一阶段：统一流程所有权与身份

先选择 Gantry 一页做完整试点，不替换整个项目。为工程、页面、节点和资源补稳定身份，建立同一份流程文档及修改命令。旧源码图和有效配置通过明确的导入差异形成基线，保留备份；转换后停止该页日常的双主恢复。暂未转换的页面继续走已验证的兼容路径，不把它们偷偷混进新协议。

### 第二阶段：共用画布，打通 VS 预览

让 VS 和 EXE 显示同一份图，再加入 VS 内打开相同编辑器的入口。复用现有动作与代码方法适配器，不重写驱动，不新增一套脚本模式。生成源码是派生交付物，不再作为另一个自动反向覆盖工程的来源。

### 第三阶段：收敛资源与编辑体验

资源目录从 UI 树中抽离；轴只显示自身绑定点位，视觉只显示实际相机/VPP能力。统一重命名、移动和删除的引用检查。节点属性保持最少步骤，业务描述优先，技术 ID 不暴露给应用工程师。

### 第四阶段：完成真实生产闭环

以点胶转盘验证并行工位、随行数据、异步结果、装盘、本地结案、MES 重试与掉电核对。完成后再决定是否值得做完整 VS 专用流程文件编辑器。优先解决设备可交付性，不先追求编辑器功能数量。

## 验收依据

- 自定义设计器删除节点后，VS 同模型预览也消失；新增、重命名和移动同样一致。
- 删除页面再创建同名页，得到新 PageId，旧节点和语言标题不复活。
- 保存、重开、放弃修改、失败回滚、三语和配方切换不改变对象身份。
- 运行期间编辑草稿不会改变当前发布计划；停止后重新初始化不会接着旧故障节点执行。
- VS 预览及编辑只读取元数据，设备连接和真实动作调用计数为零。
- 同一真实设备实例被手动界面和流程使用；断线、取消、超时和并发占用有明确结果。
- 点胶转盘验证至少两件在制品，跨转位后条码、重量和 AOI 数据不串件；MES 失败可恢复，不重做已经确认完成的物理动作。

## 开闭原则：拖拽与 DIY 的扩展契约

目标是让新增同类设备、工艺方法和复用流程通过扩展进入平台，不要求每增加一个工具就修改编辑器、运行器和主保存。核心扩展协议仍可能因全新能力而演进；开闭原则不等于从此任何代码都不能修改。

### 三条入口，统一执行

1. **直接拖拽现有动作。** 使用已配置的轴、IO、Device、VPP、常量和数据能力，工程师选择实例、参数、结果和出口。
2. **DIY 普通业务方法。** 现有父类的派生对象公开方法自动发现，当前 Form 的无参 ResultType 方法继续适配。无需再实现一个工具登记工程。后续可将复杂工艺迁移到独立工艺服务，避免长期依赖 Form 私有字段；旧方法仍兼容。
3. **封装子流程模板。** 工程师将一组节点封装为“扫码入料”“点胶检查”等工具，声明输入输出和所需资源角色。实例化时绑定现场实际对象。定义可复用，每个实例的节点 ID、计时、数据和运行状态独立。这是待实现能力，不是恢复已经移除的代码模块或脚本编辑器。

三条入口都形成相同的动作描述和节点实例：输入输出契约、实际资源绑定、执行方式、结果、取消、超时、报警、重试及调试。普通动作输出数据后由条件决定出口；原生 ResultType 方法决定 NEXT/CASE/IDLE/End，图只保存去向，不叠加另一套冲突判断。

### 用户最少写多少代码

在已经实现连接和业务基础成员的 AbstractDevice 派生类内，新增一个公开方法即可作为普通工具发现，例如：

```csharp
// 以下成员放入已有设备派生类；不是一个可单独替代驱动的完整类。
[AlphaRap.FlowProgramming.FlowTool("重量判定", "Check weight", "Comprobar peso",
    Id = "project.weight.check", UsesHardware = false)]
public bool CheckWeight(double actual, double lower, double upper)
{
    return actual >= lower && actual <= upper;
}
```

FlowTool 特性在当前实现中是可选的：用于稳定动作 ID、三语名称及模拟说明，不加也会按方法名发现。应用工程师拖入后把 actual 绑定称重结果，lower/upper 绑定 Recipe，下游按布尔结果选择正常或 NG 分支。参数支持范围由现有签名适配器决定；任意泛型、复杂对象及第三方类型不会天然变成可编辑字段，后续须通过统一类型描述器扩展。

### 扩展发现的边界

当前 FlowInheritedMethods.RootType 仍列举若干支持的父类；新增这些父类下的具体设备不用改核心，增加全新品类仍可能改该目录。建议下一步把类别识别、对象工厂和方法描述作为统一适配器目录扩展，替代分散 switch。该目录由 SDK 扩展层维护，不要求每个应用工具再实现独立注册接口。

浏览类型只生成元数据，不实例化、连接或调用驱动；实际对象来自原资源页面。不会因为发现一个相机类就在工具箱制造未配置的 Camera1。增加能力通常需要编译部署；新增现场实例、修改绑定或组合已有流程则不需要重新编译。

### 执行与版本规则

- 新动作只实现业务，沿用同一保存、资源租约、取消、计时、报警、日志和调试路径。
- 不能从任意 C# 函数自动推断全部硬件占用，也不能强制安全终止任意阻塞回调。跨资源工艺需要声明资源和完成策略，保留实际调用退出屏障。
- 原生 IDLE 是轮询契约，不代表每次都可重发非幂等命令。执行状态按节点调用或产品隔离；新组合动作应区分首次进入、等待和完成。
- 重试策略须区分安全可重试与需要确认的动作，不能因网络上传失败而重新点胶。业务事实与流程出口放行分开记录。
- 动作与模板有稳定 ID 和版本。增加能力不静默改变已有实例；删除或改变端口/签名，影响清单要求明确重绑，不自动选同名替代方法。
- 发布时验证描述、类型、绑定、版本和图；执行时验证相关资源反馈。继续不做全机轴/IO就绪扫描。

### 建议实施先后

先将已有动作和原生函数适配统一，并完成一页共享工程闭环；再补类别/类型扩展目录和子流程模板；最后以点胶转盘验证产品上下文、本地持久记录与 MES 待传。VS 与应用共用流程工程和编辑规则。新增能力不再要求两边同时维护控件定义。

## 核查位置与外部依据

- `AlphaRap/FlowProgramming/FlowPrograms.cs`：草稿恢复、源码控件兼容、发布快照、原生代码调用入口。
- `AlphaRap/FlowProgramming/FlowControlSource.cs`：源码布局和事件快照、删除来源识别。
- `AlphaRap/FlowProgramming/FlowSourceGenerator.Render.cs`：当前仅生成 FlowProgram/FlowStep 构造代码。
- `AlphaRap/Configuration/ProjectConfiguration.cs`：统一保存、文件暂存、外改检测及回滚。
- `AlphaRap/FlowProgramming/FlowResources.cs`、`FlowActions.cs`、`FlowInheritedMethods.cs`：实例目录、动作契约、资源租约与继承方法发现。
- `docs/RotaryProductTraceability.md`：产品随行数据提案，不能按已实现能力使用。
