# 面向应用工程师的 FlowChart 设计器方案

日期：2026-10-22。状态：设计提案，未实现新运行器，未更换现有 NPSDK.dll。

## 判断

可行性高，值得做成框架的长期主线。当前已有 Flow_Chart 图形节点、流程分支、模块、IO、运动、视觉和 MES 等业务入口，能够复用现有设备能力。主要建设量在动作契约、运行器与调试体验；图形拖拽只是用户入口。

目标是让助理工程师通过选择目标、填写参数、绑定结果和连接分支完成标准流程；资深工程师编写并验证可复用动作，框架维护者负责运行语义和驱动。具体减少多少代码，应由试点统计，不能在尚未实现时承诺比例。

## 工程师的使用过程

1. 从设备模板创建项目，配置板卡、轴、IO、相机、PLC 和 MES 连接。执行独立设备检查，设计模式不连接真实硬件。
2. 选择工艺模板，如“扫码—移动—拍照—判断—保存—上传”。新手先使用有明确顺序的步骤列表；复杂分支使用同一模型的流程图视图。
3. 从动作目录选择动作，按目标类型筛选可用设备或模块；界面用名称、说明、单位、默认值和实例引导，不要求填写类名和函数名。
4. 参数使用点位选择器、设备下拉框、枚举和数值编辑器；结果绑定通过“前面节点 → 输出字段”选择，发布前检查类型、单位和分支上的可用性。
5. 执行配置检查和真正隔离硬件的仿真。错误直接定位到节点与字段，显示如何修正。
6. 调试时查看当前节点、等待条件、剩余超时、实际参数和结果；支持执行前断点、单步、变量监视及结构化日志。真实动作的单步、重试和节点重跑仍受权限与机器状态约束。
7. 发布不可变的流程版本，并绑定动作目录版本及设备配置版本；操作员只运行已发布版本。编辑草稿不改变正在运行的流程。

## 结构与设计模式

### 设计器：MVP 与统一流程模型

设计器负责步骤列表/画布、连线、参数面板、校验提示和版本差异。Flow_Chart 可作为现有 WinForms 图形视图兼容保留；不再让它拥有工作线程。设计器可先作为框架工程模式页面，后续复用同一模型和运行内核形成独立编辑程序，不必第一阶段就做两个应用。

流程模型保存稳定 NodeId、ActionId、ActionVersion、TargetId、输入绑定、结果端口、控制连线、超时和错误策略。初期沿用框架熟悉的版本化 XML 即可，持久化格式并不是关键难点。画布坐标是编辑信息，不参与执行。

### 动作目录：命令、策略和厂商适配器

动作目录显式登记 ActionId → 参数描述及执行工厂。描述包含名称的语言键、目标类型、输入输出类型/单位、超时、资源需求、前置条件和重试属性；执行器完成真实动作。按功能建立少量接口，避免通用基类层层包装。

可用目录包括：轴/模组移动、气缸伸缩、IO 写入、IO 读取、IO 等待、PLC 读写、视觉运行、条件判断、数据保存、MES 上传、报警、自定义动作和子流程。

“读取 IO”返回一次有效采样；“等待 IO”等待电平或新边沿，两者分别提供。气缸等常用工艺应成为带互锁和到位确认的完整动作，不让新手每次拼接多个底层 DO/DI。

模块动作的粒度应表达工艺，如“取料模组.MoveTo(拍照位)”或“夹紧并确认”。复杂成熟工艺可封装为子流程，支持有类型的输入、输出和错误端口。流程共享用引用版本的子流程实现，避免复制整张图。

### 运行器：显式状态机与每流程顺序调度

FlowRuntime 独立于 WinForms。加载流程后先校验，再生成可执行计划；每个流程实例默认顺序推进节点，不为每个节点新建线程。同一流程可以等待异步操作而不阻塞 UI；跨工位并行由后续明确的并行/汇合节点支持，不依赖节点各自抢线程。

运行状态包括未就绪、就绪、运行、暂停、停止中、完成、取消、故障。节点展示状态包括待执行、执行中、等待条件、完成、失败和取消。等待中的动作仍属于同一次执行，不能每次轮询重新发送运动或 MES 请求。旧 SDK 的轮询动作可通过“开始一次、检查多次”的兼容适配器接入。

每次产品/工位执行建立独立上下文，持有 RunId、产品 ID、流程版本和类型化变量。完成结果包含输出及分支；取消和失败为明确终态。UI 订阅状态快照，在 UI 线程更新颜色和耗时。发布后的计划和本轮配方快照不可被在线编辑修改。

### 资源与依赖：设备会话及显式对象解析

TargetId 在执行时由设备/模块注册表解析成受管理的实际实例。这允许同一流程模板换绑不同轴、工位和相机，也允许连接恢复时更新底层连接，但稳定业务身份不变。对象归设备会话管理，不能用控件 Name、页面对象或序列化的任意 CLR 对象作为运行依赖。

调用链是：节点配置 → 已登记动作 → 解析目标实例 → 执行具体业务方法 → 返回结果。允许扩展包在受控加载时扫描明确标注的动作并生成目录；加载后校验动作 ID、版本和参数契约。不给普通流程作者“任意程序集＋类名＋方法名＋字符串参数”的反射入口。那会把类型错误和重构问题推迟到设备运行时。

### 数据与消息：仓储和可选的持久待发送队列

数据保存动作使用统一数据入口。MES 在线请求与可靠补传分别设计；需要离线补传时，先保存带业务请求 ID 的待发送记录，再由发送器处理回执。请求超时不代表服务器未处理；重试依赖服务端幂等/查单能力，不能声称天然做到恰好一次。

## 示例：工程师实际配置的节点

下列参数和超时是设计示例，并非现场建议值。

### 等待产品到位

- 动作：`io.wait`；目标：进料到位输入。
- 参数：条件：有效值为 ON；模式：进入节点后等待新上升沿；超时：5000 ms。
- 输出：触发时间、有效采样、产品周期 ID。
- 执行对应：已登记 IO 动作 → 输入设备会话 → 等待满足条件。
- 失败处理：通信故障、信号过期、超时分别报告；前一周期残留 ON 不算新产品。

### 模组移动到拍照位

- 动作：`module.moveTo`；目标：取料模组。
- 参数：点位：配方.拍照位；速度：配方.拍照速度；超时：10000 ms。
- 输出：实际位置、完成时间。
- 执行对应：模块动作目录 → 取料模组实例 → 经校验的 MoveTo 动作。
- 失败处理：权限、互锁、资源和就绪检查通过才发命令；取消后必须确认设备已停止。

### 运行视觉定位

- 动作：`vision.run`；目标：TakePCBA / 稳定 VppId。
- 参数：等待模组移动完成；超时：3000 ms；参数来自配方。
- 输出：X、Y、Angle、OK、RunId、图像引用。
- 执行对应：视觉动作适配器 → 现有视觉运行接口 → 按 RunId 返回结果快照。
- 失败处理：超时晚到结果不能进入下一周期；补偿另设显式动作，由应用者决定是否使用。

### 判断检测结果

- 动作：`condition.compare`；目标：本产品上下文。
- 参数：左值：视觉定位.OK；运算：等于；右值：true。
- 输出：OK / NG 控制分支。
- 执行对应：受限类型化条件求值 → 选择分支。
- 失败处理：缺少输入是配置或运行错误，不能默认为 NG；X/Y 单位和绑定类型需在发布前检查。

### 保存生产记录

- 动作：`data.saveProduction`；目标：生产数据存储。
- 参数：产品 ID、条码、视觉定位输出、判定、流程版本。
- 输出：记录 ID、保存结果。
- 执行对应：数据动作 → 单一数据写入入口 → 可追溯结果。
- 失败处理：写盘失败进入明确错误分支；防止手动重跑节点产生重复业务记录。

### 上传 MES

- 动作：`mes.upload`；目标：已配置 MES 连接。
- 参数：产品 ID、记录 ID、判定；凭据引用受控配置；请求超时：5000 ms。
- 输出：MES 回执、业务状态、请求 ID。
- 执行对应：MES 动作 → 业务协议适配器 → 请求记录与回执处理。
- 失败处理：网络超时可能已被服务器接收；只有幂等键/服务端去重或查单确认后才能安全重试。

视觉 OK/NG 两条分支均应有明确出口，可分别执行对应处置后汇合到保存及上传。通信异常、配置错误与产品 NG 必须分开，不能全部汇成“检测失败”。补偿读取和应用另设显式动作，维持“由应用流程主动添加”的现有约定。

## 必须先明确的运行规则

- 启动：校验完整计划、设备就绪和数据绑定后运行；同一流程重复启动不得创建多个执行实例。
- 暂停：先定义是否只停止推进后续节点，当前动作如何停由动作和设备能力决定；不能把冻结画布颜色当成暂停运动。
- 停止：阻止新动作，向当前动作发取消，再确认设备停止；不支持取消的设备操作必须有超时及故障结果。Task 取消不等于电机已经停下。硬件急停与软件调度分别负责各自职责。
- 资源：动作按设备资源声明占用，同轴、相机和连接不得被不同流程无序争用。先做资源忙时拒绝或有界排队；多资源动作规定获取顺序，避免互相等待。
- IO：区分有效 OFF、通信失败和过期数据。等待新边沿需定义订阅时点及进入节点时已有 ON 的处理；重要信号的采样和锁存要求需由设备规格决定。
- 超时：节点有总截止时间；重试不能无限延长工艺等待。失败应保留输入、目标、错误码和上下文。
- 重试：读状态与有副作用命令分开。运动、夹爪、保存和 MES 操作必须声明是否可重试，未知状态不能自动重复执行。
- 恢复：首次只支持从明确的工艺边界恢复或重新开始。任意节点断电续跑需要真实位置、在制品和外部系统状态核对，不能简单恢复一个节点编号。
- 校验：检查重复 ID、断开的必要出口、不可达节点、参数类型、设备能力、循环等待/退出条件和分支内变量可用性。允许有明确等待与退出的工艺循环。
- 实时性：流程引擎适合工艺协调；确定性多轴插补、精准触发和硬件联锁仍由控制器、驱动和经过验证的模块完成。

## 让助理工程师更容易掌握的重点

动作目录首先提供常用模板和业务名称，底层高级参数按权限展开；统一显示“当前等什么、已经等多久、下一步怎么处理”。参数错误在保存/发布阶段解释，运行失败同时展示业务提示及可展开的原始错误。

流程运行记录应能按产品 ID 回放节点输入、输出、耗时和分支，但回放默认只读，不能自动重发设备命令。子流程提供示例和使用说明。加入简单练习项目：仿真 IO → 结果判断 → 保存，再逐步加入运动、视觉和 MES。

语言使用现有中英西语言机制；ActionId、NodeId、TargetId、变量键和分支代码保持稳定，标题与描述使用语言键。切换语言不重建正在编辑的参数。固定布局沿用 Designer/.resx，动态节点和参数面板复用可预览 UserControl 模板。

## 分阶段落地与可行性判断

### 第一步：先验证运行内核和动作契约

先修复已发现的启动/停止竞态、仿真隔离、IO 质量与驱动结果语义。选取一个工位，登记 IO 等待、模组动作、视觉、条件判断、数据保存、MES 请求及子流程所需的最小动作集。用代码或配置构建计划，脱离 UI 进行驱动替身测试。

验收：动作只派发一次；停止后不产生下一动作；超时晚到结果被隔离；同设备资源互斥；无界面可运行；仿真路径不碰真实驱动。

### 第二步：提供应用端设计和调试闭环

提供动作选择、设备选择、类型化参数、结果绑定、分支连接、校验、仿真、断点和版本发布。保留原 Flow_Chart 和旧委托流程入口，新旧流程由明确执行入口选择，禁止两套引擎同时驱动同一工位。旧流程的委托内容未必能自动转换，初期使用兼容动作，逐步人工迁移并核对。

验收：助理工程师通过设备配置及模板完成一条“到位—拍照—判断—保存—上传”流程，无需编辑其重复状态判断代码；参数错误和断线都能定位至节点。

### 第三步：在复用得到验证后增加高级能力

再增加共享子流程、受控动作扩展、并行/汇合、流程版本差异、MES 离线补传及有边界的恢复。不要把任意脚本、任意对象调用、复杂并发和断电续跑同时塞进第一版。

试点度量由工程师实际操作获得：首次独立完成流程所需时间、每次新流程的 C# 修改量、复制代码量、故障定位时间、流程发布缺陷和动作复用情况。以现有手写流程作为对照，再决定推广范围和投入。

## 现有框架可复用与需建设的部分

可复用：现有运动/IO/PLC 适配、视觉 RunId 与快照、配方和点位、MES 业务实现、语言登记与 WinForms 设计器基础。现有缺陷先按 [核心审查建议](FrameworkUpgradeReview.md) 修复，不能直接把有问题的返回值包装成可视化动作。

需建设：独立运行器、动作元数据与注册、稳定目标注册表、流程模型及版本迁移、类型化变量绑定、发布校验、调试快照与资源协调。技术可行性高；对标准工艺的收益有合理依据；全自动兼容任意旧委托或任意动态方法、任意位置断电续跑不应承诺。

本提案基于已审查的 NPSDK 实际 DLL 与 AlphaRap 调用关系，未引入新的第三方工作流产品，未修改业务代码，未验证真实硬件。配套交互图仅解释节点配置，不连接设备，也不是已实现的 FlowChart 产品功能。

## 提案验证

已检查文档引用的本地报告存在，配套交互图使用本机 Canvas SDK 声明执行 TypeScript 检查，诊断数为 0。该验证仅覆盖文档引用和类型，不等同于界面实际渲染、运行器实现或设备验收。

## 从现有代码到可交付功能的复核

进一步核查确认：这是能在本框架上实施的功能建设，现有模块可以复用，但尚未具备完整的配置运行能力。以下“存在接口”只表示接入基础存在，不表示该接口已满足新运行器的全部契约。

- **IO 与气缸：** NPSDK NP_Input.IsOn、NP_Output.On/Off 和 NP_Cylinder.On/Off 已存在。[上料流程](../AlphaRap/TaskProcess/UpConveryor.cs) 的多个节点反复执行输出并判断到位，适合提炼为“气缸动作并等待”。需要补齐有效采样、动作完成/失败区别、超时及取消。
- **轴与模组：** NP_Motor.Goto/Home/GetPos 等可作为动作后端；现有点位控件可以提供点位编辑基础。自动流程不能依赖当前选中行或手动按钮事件，需要稳定点位 ID 和不依赖选择状态的执行入口。
- **视觉：** [VisionproInterface](../AlphaRap/Vision/VisionproInterface.cs) 已有 TryRunTB、LastRunResult、TimeoutRun、CancelRun。[Gantry](../AlphaRap/TaskProcess/Gantry.cs) 已将开始与检查同编号结果分开，这是动作化的直接基础。仍需稳定目标解析和统一结果契约。
- **数据：** [ProductionDataStore.Append](../AlphaRap/Classes/ProductionDataStore.cs) 可脱离保存按钮调用；需要类型化字段映射、稳定业务记录 ID、列版本和一致错误结果，已有 CSV 缺陷仍须修复。
- **流程：** [Gantry.Designer](../AlphaRap/TaskProcess/Gantry.Designer.cs) 保存 Next/Casse1 等控件引用和 FlowChartRun 委托绑定；实际 Flow_Chart 还拥有执行线程。独立流程模型、运行时编辑器和发布校验需要建设，不能把现有 VS 设计器配置等同于现场流程设计器。
- **运行入口与后台：** [MiddleLayer.RunControl](../AlphaRap/Core/MiddleLayer.RunControl.cs) 控制全局模式并启动 NPSDK 流程，[FlowControl](../AlphaRap/Controls/FlowControl.cs) 另外扫描 IO、模块周期及电机保护。新运行器必须明确接管哪条工位流程，常驻保护保持独立，不能同时开启两套执行器控制同一设备。
- **报警：** [AlarmCatalog](../AlphaRap/Classes/AlarmCatalog.cs) 已有三语目录及主表行为属性，[MiddleLayer.Alarms](../AlphaRap/Core/MiddleLayer.Alarms.cs) 已有运行表桥接，可提供报警选择器。需要事件上下文、去重及活动实例管理；语言重载清空活动报警等问题不能被带入新设计。
- **上传：** 此方案不以当前 MES 页面或其函数结构作为约束。上传是具有请求、回执、业务拒绝、未知结果和重试策略的一类外部动作，可接不同 MES、数据库或服务；业务协议由适配器实现。

初期可以在 .NET Framework 4.8 宿主内新增无 WinForms 依赖的流程契约和运行内核，由宿主适配层连接现有设备对象。无需为了试点先重写全部 NPSDK，也不承诺现有 WinForms 设备对象已可脱离宿主独立运行。

## 完整数据链：触发、执行、分支、保存和上传

### 触发先形成一次运行请求

按钮、PLC 请求、IO 边沿、扫码、上位机消息均转换成具有来源、时间、设备/工位、条码及请求 ID 的触发数据。先检查运行权限、工位就绪及忙状态，再创建 RunContext。对重复触发采取拒绝、合并或有界排队，由工位明确配置，不能为每次轮询到 ON 都新建流程。

初始化、自动、手动及受控恢复分别有执行入口；常驻监控、保护和报警响应独立于正常生产步骤。产品流程未走到某个节点时，保护也必须持续有效。

### 数据属于本次产品和本次节点执行

每个运行上下文包含 FlowId/流程版本、RunId、工位与产品 ID、配方快照及版本、触发信息、节点结果。RunId 应跨重启可区分，并在需恢复时持久化。产品 ID 不等于运行 ID，返工和重复检测必须保留独立运行记录。

每个节点结果分成三部分：执行结果（完成/失败/取消）、类型化输出、诊断（目标、开始结束时间、错误码及调用次数）。产品 OK/NG 是业务输出，不与设备调用失败混为一谈。节点执行中可展示等待状态，输出在本次动作完成后按契约一次性发布，禁止读到上一周期或半更新的结果。

节点输出按 NodeId 和本次执行编号命名空间保存，例如 VisionLocate.X、VisionLocate.Y、VisionLocate.Angle、VisionLocate.RunId。输入可以来自常量、设备配置、冻结配方、触发数据、前驱输出或受限计算。内部绑定使用稳定 ID，不依赖可翻译标题。循环中的同一节点有不同执行编号，旧输出的保留与当前迭代取值必须明确。

图像和大型视觉记录使用有生命周期的引用，不在每条边上复制完整对象。要长期追溯时，先把图像保存为受管理文件或制品，再持久化稳定引用；临时内存对象地址不能作为长期记录。

### 分支传递的是明确的输入绑定

可以传递给下一分支。连线决定下一步执行哪个节点，输入绑定决定该节点读取哪些结果；两者分开存储和校验。下一分支可以只取需要的字段，也可以传递一个有固定结构的检测结果对象。

一份冻结结果可供多个后续节点读取，不允许各分支原地修改同一个共享对象。只有某分支产生的数据，在其他分支或汇合处可能不存在；编辑器应提示路径依赖，要求显式合并字段、可选值或回退策略，不能悄悄当成零或 false。

并行后汇合需要声明等待全部/任一及失败处理，结果按分支命名；共享变量更新必须有明确合并规则。跨工位使用带产品 ID 的交接消息或队列，不用全局变量传递“最后一次结果”。第一版先做好顺序分支和子流程，再做并行。

### 从结果形成一份可追溯生产记录

例如：触发输入条码 → 等待到位 → 模组移动 → 视觉结果 → 判定 → 生成生产记录 → 保存 → 创建上传任务 → 取得外部回执。

生产记录至少包含 RecordId、RunId、产品/条码、流程及配方版本、设备/工位、关键结果与单位、判定、时间、图像引用及相关报警。记录快照与运行上下文分开，不能由上传动作稍后去读取一份已经变成下一产品的数据。

保存节点返回 RecordId 和保存状态，下游绑定这条记录进行上传。业务字段使用正式序列化与明确列/结构版本，存储数值与 UI 语言文化分离。记录不必包含所有临时变量，只保存工艺所需及追溯所需信息。

### 保存与上传分别跟踪结果

检测结果、保存结果和上传结果是三个维度。产品可以检测 OK 但上传失败，不能因此覆盖原始判定；系统故障也不能静默落成产品 NG。

允许业务选择“上传成功才放行”或“本地可靠保存后放行、后台补传”。需要可靠补传时，生产记录与待发送项应在支持事务的持久存储中一起提交，或采用明确可恢复的写入协议。仅先写 CSV、再写内存队列，不能保证崩溃后补传完整。

上传任务引用已保存的记录快照、目标服务及业务操作 ID；状态可为待发、发送中、已确认、明确拒绝、结果未知和待重试。进程退出后仍可恢复未完成任务。队列有容量、过期和人工处理规则，达到上限时明确阻止继续接收或按业务政策处置。

网络超时可能已经提交到服务器。相同业务操作重试使用相同幂等键，尝试编号另记；返工和新检测使用新的操作身份。对端不支持幂等时，需要查单/对账或人工处理未知结果，不能承诺恰好一次。多个上传目的地各自保留回执，不共用一个全局 UploadOK。

凭据保存在受控连接配置中，流程只引用连接 ID；日志保留可追溯请求信息，避免把凭据混入产品输出。

## 报警绑定与下一步条件编辑

### 节点绑定已有报警目录

节点的错误配置可以选择“执行异常报警”“超时报警”，并关联目标设备及动态参数，例如产品 ID、实际位置、超时时间。固定内容仍使用已有三语言目录与占位符。报警代码、类型和停机行为遵循主定义；流程作者不能通过修改节点文字覆盖停机规则。

一个节点可在需要时提供显式业务报警动作；外部保护触发的报警仍由中央报警服务接收并通知运行器，不依赖当前节点被执行。每次报警带 RunId、NodeId、目标 ID 和发生时间；同一次故障轮询不重复刷屏，新周期故障与旧故障有独立身份。

报警确认、故障恢复和流程恢复分别处理。确认报警不代表设备故障消失，也不代表可以自动恢复运行。普通分支不能绕过有效停机报警。故障诊断记录由运行器保证写出；恢复或收尾动作只执行明确授权的设备策略，不能假设所有输出一律 OFF 都是正确的机械处置。

### 用可视化条件构建器编辑出口

条件编辑器提供“来源字段 → 比较方式 → 对照值 → AND/OR 分组 → 目标节点”。支持布尔、数值区间、枚举、字符串以及有效性检查；阈值可绑定配方。普通工程师无需写 C# 表达式。内部保存受限的类型化条件树，禁止把任意代码表达式直接编译执行。

对于视觉节点，示例出口为：

- 执行超时/异常：进入错误策略并触发所绑定报警，按主定义暂停或停机。
- 执行成功且本次 X/Y/Angle 满足配方范围：进入 OK 处置。
- 执行成功但不满足判定：进入 NG 处置。
- 必要输出缺失、编号不匹配或数值无效：进入数据/执行故障，不当作合法 NG。

实时 IO 条件与已完成节点的结果快照要在界面中区分。普通分支条件在节点结束后对确定快照评估一次；“持续等待直到条件成立”使用等待节点，具备截止时间、取消和输入质量检查。

默认采用可验证的单出口或明确命名结果端口。允许多条条件边时，定义互斥校验或可见的先后优先级、默认出口；不会因为画布连线顺序不同而改变业务。需要同时执行多路时使用显式并行节点。

## 交付前应验证的完整链路

使用替身设备和替身上传服务验证：重复触发仅创建约定数量的运行、迟到视觉结果不进入下一产品、分支结果绑定类型正确、缺失值不能被误判、同一动作不会反复发送、停止后无新动作、保存失败不会伪装成功、进程重启后待上传记录仍可发现、上传响应丢失后的未知状态可被处理。

随后在单工位核对设备完成状态、互锁、暂停/停止及工艺处置。上线评估覆盖的是完整链路，不是只有画布可以拖拽。这一功能的技术可行性高，关键建设工作集中在数据契约、生命周期和异常语义，收益在标准动作与模板积累后体现。
